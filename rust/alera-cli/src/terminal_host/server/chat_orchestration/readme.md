# chat orchestration host service

Delegation, messages and task tracking between agent chats, on top of `AgentChatRuntime`. It is separate from terminal orchestration: its own verbs (`chatOrchestration.*`), tables (`chatOrchestration*`), event and identity. The product contract is `docs/agent-chat-orchestration.md`; this file is the wire and in-process contract.

## Capability

`chatOrchestrationV1` is advertised in the control file, `status.get` and `MOBILE_HELLO_CAPABILITIES`. It is additive and does not bump `aleraTerminalHostProtocolVersion` or the mobile protocol version.

## Caller identity

| Connection | Scope | Actor | Authority |
| --- | --- | --- | --- |
| Desktop app | `desktop` | `desktop` | Human: every verb, every chat |
| Local CLI without a credential | `cli` | `cli` | Human: every verb, every chat |
| Paired phone | `mobile:<deviceId>` | `mobile:<deviceId>` | Human: same verbs as desktop |
| Chat-bound agent | `chat:<chatId>` | `agent:<chatId>` | Bound agent rules below |

The scope and actor always come from the connection; payload fields such as `actor`, `from` or `scope` are ignored.

### Chat credential

- The host mints one credential per chat generation in a `ProviderLaunchHook` before every provider spawn: an opaque random secret (64 hex characters), written to `<runtimeDir>/agent-chat-mcp/<credentialId>.token` (directory `0700`, file `0600`, owner only). Only the SHA-256 (hex) is persisted. The previous credential of that chat is revoked and its file removed on every new spawn, provider switch, close and archive.
- The injected MCP server is `alera mcp --runtime-dir <dir> serve --chat-credential-file <path>` with server name `alera`. No secret is ever on argv or in snapshots. The same hook assigns `ProviderLaunch::instructions` (`instructions`): orchestration rules for the chat's provider, each section at most 4,000 bytes, that the production factory delivers to the provider.
- The CLI reads the file (trimmed) and sends it in `hello` as `chatCredential: "<token>"`, next to the usual `token` and `protocolVersion`. A missing or unreadable file is a CLI error; the CLI never falls back to an unbound connection.
- The host verifies the hash against an unrevoked credential. A mismatch, a revoked credential, or a chat that is archived fails `hello` with `errorCode: "chat_credential_invalid"`. Success adds `chatBinding: {chatId}` to the hello response and binds the connection for its lifetime.
- Bound connections may only call `chatOrchestration.*`, `project.list`, `workspace.list` and `status.get`; anything else is refused with `errorCode: "chat_scope_denied"`.

### Bound agent rules

- Every call needs the caller chat to be unarchived with a running turn (`errorCode: "caller_turn_inactive"`), and the binding's generation must still be current (`chat_credential_invalid`). A chat whose turn ended still counts as live while its provider process runs a native sub-agent the turn started (the actor snapshot's `backgroundSubagentsRunning`), since such a background sub-agent keeps calling tools with the chat's credential; the credential itself is revoked when that process goes away.
- Reads (`list`, `read`, `task`, `tasks.list`, `wait`, `capabilities`, `requests`) and `send` / `delegate` work across every project, workspace and host this runtime knows.
- `interrupt`, `respond`, `configure` and `cancel` work only on the caller's descendants (`errorCode: "not_in_lineage"`). Humans are not limited by lineage.
- A target chat or a new child may not run in a runtime mode above the caller's (`errorCode: "mode_ceiling"`); order: `approval-required < auto-accept-edits < auto < full-access`. A child without `runtimeMode` inherits the caller's.
- `read` returns only user and assistant text and plans, for every caller.

## Verbs

Receipt-backed mutations (`delegate`, `send`, `cancel`, `interrupt`, `respond`, `configure`, `updateTitle`, and `task` with `acknowledge: true`) carry `requestId`. Receipts are keyed by `(scope, verb, requestId)` plus a canonical payload digest: the same payload replays the stored response, a different one fails with `request_conflict`. A task acknowledgement's digest contains its task id and acknowledgement action, and its bound lineage is checked before replay. New CLI and MCP acknowledgement mutations must send a request id. Legacy `task {acknowledge: true}` without `requestId` remains supported as an idempotent state update, but does not store a receipt or guarantee stable response replay or request-id conflicts. Plain task queries never acknowledge a result or record a receipt.

| Verb | Payload | Result |
| --- | --- | --- |
| `chatOrchestration.capabilities` | `{workspaceId?, hostId?, search?}` | `{maxWaitSeconds: 50, providers: [Provider + {mcpInjection {stdio, http}, orchestration {supported, reason?}, omittedModels?}], runtimeModes, ceilingRuntimeModes, caller?: {chatId, runtimeMode, providerInstanceId, model, reasoningEffort}}` |
| `chatOrchestration.delegate` | `{requestId, task, parentChatId?, title?, role?, notify?, mode?: async\|wait, waitSeconds?, agent?: {providerInstanceId?, model?, options?}, runtimeMode?, interactionMode?, target}` | `{taskId, chatId?, workspaceId?, status, result?, task, next?}` |
| `chatOrchestration.send` | `{requestId, chatId, message, parentChatId?, delivery?: auto\|queue, expectReply?}` | `{chatId, delivery, taskId?}` |
| `chatOrchestration.task` | `{taskId, acknowledge?, requestId?}` (new acknowledgements send `requestId`) | `{task, next?}` |
| `chatOrchestration.tasks.list` | `{parentChatId?, childChatId?, rootTaskId?, workspaceId?, projectId?, statuses?, attention?, limit?, cursor?}` | `{tasks, nextCursor?}` |
| `chatOrchestration.wait` | `{taskIds, waitSeconds?, until?: all\|any}` (default `all`) | `{tasks, timedOut, next?}` |
| `chatOrchestration.cancel` | `{requestId, taskId, reason?}` | `{task, cancelledTaskIds}` |
| `chatOrchestration.interrupt` | `{requestId, chatId}` | `{acknowledged: true, interrupted}` |
| `chatOrchestration.backgroundWait` | `{requestId, taskIds: 1..20 nonempty strings, waiting?: bool = true}` | `{matched, unmatched}` |
| `chatOrchestration.requests` | `{taskId?, chatId?}` | `{requests: [{chatId, taskId?, request}]}` |
| `chatOrchestration.respond` | `{requestId, chatId, runtimeRequestId, response}` | `{resolved: true}` |
| `chatOrchestration.configure` | `{requestId, chatId, providerInstanceId?, model?, reasoningEffort?, runtimeMode?, interactionMode?}` | `{snapshot}` (as `agentChat.configure`) |
| `chatOrchestration.updateTitle` | `{requestId, chatId?, title?, regenerate?}` | `{applied, title}` for a rename, `{titleGeneration}` for a regeneration (`agentChatTitleGenerationV1`; exactly one of `title` and `regenerate: true`; a bound caller's own chat when `chatId` is omitted, otherwise a chat it owns; a bound agent's title counts as `generated` and never replaces a title a person set, which fails with `titleSetByUser`) |
| `chatOrchestration.read` | `{chatId, limit?}` | `{chat, messages, plans, truncated}` |
| `chatOrchestration.list` | `{workspaceId?, projectId?, hostId?, includeArchived?}` | `{chats}` |
| `chatOrchestration.transfers` | `{chatId?}` (a bound agent defaults to its own chat) | `{chatId, transfers: [{transferId, kind, sourceChatId, targetChatId, status, sourceTitle?, taskId?, error?, createdAt, consumedAt?}]}` newest first (`agentChatTransfersV1`) |

`backgroundWait` is for bound agents only and always acts on the credentialed caller's own chat; a payload `chatId` is ignored and a person's call fails with `unsupported`. It marks (`waiting: true`) or unmarks background commands the agent waits on so the chat stays working until they end, and ids that name no running background command come back in `unmatched`. A provider without background waits answers `unsupported` with an `Invalid request` message; a chat with no live provider answers `provider_unavailable`; a provider error or a call that takes longer than 15 seconds answers `background_wait_failed`. It is forwarded from a satellite like the other verbs.

### Stop

A person's stop of a chat (`agentChat.interrupt` or `agentChat.forceStop` from the desktop, a phone or the CLI, or `chatOrchestration.interrupt` without a chat credential) first interrupts the chat's own turn, or with none running the background work earlier turns left, and then stops the delegated work under the chat, even when that interrupt fails. In one store transaction (`RuntimeStore::stop_chat_orchestration_parent`) the chat's open and sealed wake cohorts are dropped and every unsettled `delegate` or `followup` task it owns, with its descendants, gets `launchOptions.parentStopped`, which keeps it from joining any wake later. The host then cancels a sealed cohort's message if it already waits in the chat's queue, and cancels each such task with its descendants under the person's authority, like `cancel`. Each task, with its descendants, gets 30 seconds (`CHILD_STOP_DEADLINE`) to stop: one that hangs is reported in the stop's `errors` as `{taskId, code: stopTimedOut, error}` and the next task still stops; its monitor keeps driving the cancel. A `message` task (a `send` that expects a reply from another chat) is left to that chat. A bound agent's `interrupt` of a descendant does not cascade. `ChatOrchestrationService::stop_chat(.., stop_delegated_tasks: false)` is the internal opt-out for a caller that stops the descendants itself. A hub stops a remote chat's delegated tasks itself, as it owns the ledger.

`target` is exactly one of `{chat: {chatId}}`, `{workspace: {workspaceId}}` or `{newWorkspace: {projectId, hostId, mode: worktree|shared, branch?, sourceBranch?, reuseExistingBranch?, name?, parentWorkspaceId?, setup?: inline|deferred}}`. `hostId` is `local` or an SSH target id and is never implied. New workspaces are created through `workspace.createManaged` (worktree) or `workspace.createShared` (shared) on the host's own client, so setup, barriers, remote routing and broadcasts are the ordinary ones. Nothing selects a workspace or tab.

`mode: wait` returns once the task leaves `preparing|running`, or after `waitSeconds` (default and maximum 50; a larger value waits 50). `wait` is bounded the same way; call it again to keep waiting. `null` for an optional `waitSeconds`, `agent`, `agent.options` or `statuses` is the same as leaving it out; a `tasks.list` limit above 200 reads 200. A provided acknowledgement `requestId` stays strict, `null` included.

`next: "Completion wakes this chat, so end your turn. Do not wait on it or poll it."` sits beside the task (never inside it) in a `delegate` and `task` response, and in a timed-out `wait` when every open task qualifies, when the task will wake the bound caller: the caller's chat is its parent, it is `preparing|running`, `notify` is not `never`, its result is not acknowledged, and its person did not stop the parent. People and other chats never get it.

`notify`: `always` (async default), `settled_only` (wait default; becomes `always` when the wait times out), `never`.

With `chatOrchestrationPersonParentV1`, authenticated desktop, local CLI, and paired-phone callers may set `parentChatId` to an existing unarchived local or remote chat. The task belongs to that parent's dock, active task lineage, and wake delivery while its actor remains the person and its brief has no `senderChatId`. Omitting the parent keeps standalone tasks. A bound agent's parent always remains its authenticated chat; a conflicting payload fails with `not_in_lineage`. Satellite reverse callers cannot claim person parent authority. `send` ignores a person's parent when `expectReply` is false. Caller and lineage authorization precede receipt lookup. A matching receipt replays its stored response during a native freeze; a changed digest still fails with `request_conflict`. Only new requests apply the `nativeOperationPending` or `nativeOperationUncertain` parent/destination check before workspace preparation or native input. The store also checks the parent, resolved root, child, and existing-chat destination atomically at task creation, so a freeze observed during atomic task admission prevents the task and subsequent workspace effects.

With `chatOrchestrationEffortV1`, `agent.options` accepts only `reasoningEffort` as a nonempty string; omit it for the default. A bound agent's delegation to a new chat (`workspace` or `newWorkspace`) defaults `agent.providerInstanceId` to the caller's instance and `agent.model` to the caller's model on the same instance, and inherits the caller's effort when instance, model and host match and `agent.options` is absent or null; `{}` clears it and an explicit effort wins. A child creation refused for an inherited effort is retried once without it (`delegation_inheritance`). Launch options and the task record `reasoningEffort` and `reasoningEffortSource: explicit|inherited`. A new chat without any provider instance fails with `providerUnavailable` before its workspace is prepared. People and existing chat targets inherit nothing.

For a bound caller, and for anyone who passes `search` (at most 200 characters), `capabilities` shortens each provider's `models` (`capability_models`): hidden models go (never configured ones or the provider default placeholder), the rest follow the person's model order, and at most 8 are listed plus pinned ones (configured, default, favorite, the caller's own); Codex, Claude, Grok and Muse list every model. `search` keeps the first 8 models whose `"{id} {label}"` contains every word, case-insensitively. `omittedModels` counts the rest when above 0. A person without `search` keeps the full catalog. Unknown keys and non-string efforts are rejected. The destination runtime validates the selected model's verified effort support before creation or message admission, including on a remote host. Delegating to an existing chat does not implicitly replace its provider or runtime policy: incompatible explicit settings fail, and the caller can configure an eligible idle chat first. A differing model is accepted only when the target can honor it for that turn.

For `configure`, omitting `model` or `reasoningEffort` preserves the current selection; explicit `null` resets it to the instance/provider model default or default effort. This distinction is preserved through remote operations and receipt digests. Model or instance changes can clear an incompatible effort according to the chat runtime's configuration rules. Runtime ceilings remain derived from the authenticated caller.

### Task

The store record is internal; the wire task is a projection:

`{taskId, kind: delegate|message|followup, status, parentTaskId?, rootTaskId, depth, parentChatId?, childChatId?, workspaceId?, projectId?, hostId?, target, title?, role?, brief?, notify, attention: bool, attentionKind?: needs_input|failed, inputOwner?: parent|person, resultDelivery: pending|notified|acknowledged, result?: {text, truncated, turnId?}, error?: {code?, message}, pendingRequestCount?, provider?, providerInstanceId?, model?, runtimeMode?, reasoningEffort?, reasoningEffortSource?, followupOf?, link?, labels?: {parentChatTitle?, childChatTitle?, projectName?, workspaceName?, hostLabel?}, actor, createdAt, updatedAt, completedAt?}`

`status`: `preparing|running|needs_input|completed|failed|interrupted|cancel_requested|cancelled`. A task completes when the child's turn started for it (matched by `clientMessageId`) settles; its result is the main agent's last non-blank assistant message (bounded), never an item a native sub-agent reported (`parentItemId`) or a split message's segment (`continuationOf`), on both the live and the durable path. An open child request moves it to `needs_input`; answering moves it back to `running`. `brief` is the task text, bounded like the result. `attention` is true for `needs_input`, and for `failed` until the result is acknowledged. `task` with `acknowledge: true` acknowledges a settled result without changing its status; an unsettled task fails with `task_not_settled` and does not consume the request id. Reading without acknowledgement never writes a receipt or takes the result from its parent.

#### Holds and follow-ups

A `completed` head turn does not settle a task while the child still works (`monitor_hold`): no active turn but a `running|waiting` session, an open request (requests with no `turnId` count while held, toward `needs_input`), a queued message, `backgroundSubagentsRunning`, unsettled tasks the child delegated with `notify` other than `never`, or wake cohorts awaiting delivery to the child (the pump is nudged). A later turn that continues the work (turn `origin` `backgroundContinuation` or `goalContinuation`, or a first user message of origin `subagentWake` or `orchestrationWake`, read from the durable turn) moves the head with a compare-and-set that bumps no revision and records `launchOptions.chainStartTurnId` once; any other turn ends the chain. The task settles once the child shows no leftover work with an unchanged cursor for 500 ms; status and error come from the head turn, the result is the newest main answer from the chain start to the head, and restart recovery settles a held task from the same chain. A `cancel_requested` task, or a head that failed or was interrupted, is never held. Cancelling a task past its first turn, or a follow-up, interrupts its head turn when it runs instead of cancelling the brief's message.

A turn a child starts after its latest delegated or follow-up task settled `completed` or `failed`, with a parent, `notify` other than `never` and no `parentStopped`, opens a `followup` task (`followups`, from the wake pump's subscription) when no task owns that turn and the turn is a continuation, a wake, a person's message or the parent's own untracked `chatMessage`. `RuntimeStore::create_chat_orchestration_followup` dedupes on `(childChatId, childTurnId)`, refuses while the child has an unsettled task, hangs the follow-up under the chain's original task (`launchOptions.followupOfTaskId` names its predecessor, wire `followupOf`), copies notify, title and launch options without `waitNotify`, links the turn and moves it to `running` in one transaction. Its own settle joins a new wake cohort, so the parent is woken again. A bound agent's delegation during a continuation turn hangs under the task that owns that turn.

## Chat summary and read

`chat` is the agent chat summary plus `projectId`, `hostId`, `runtimeMode`, `lineage {parentChatId?, taskId?, role?}` and `link`, `[title](alera-chat://v1/<chatId>?workspace=<workspaceId>)` with the title kept to one line (the chat id when empty); tasks with a child chat carry the same `link`. `read.messages` are `{itemId, role: user|assistant, text, createdAt, origin?}` with `origin {kind: user|chatMessage|orchestrationWake|subagentWake, senderChatId?, taskIds?, requestIds?}`; `read.plans` are `{itemId, explanation?, steps: [{step, status}]}`. No reasoning, tool payloads or raw provider data.

## Events

`chatOrchestrationChanged {taskId, parentChatId?, childChatId?, workspaceId?}` to every authenticated local and mobile client after the change is committed. Clients reload the task or list.

## Parent wakes

A wake is a message into the parent chat with `origin {kind: orchestrationWake, taskIds}` and the cohort's stable `clientMessageId` (`chat-orchestration-wake:<parentChatId>:<generation>`). Only a settle joins a cohort. Its text (`wake_text`) has one block per entry in order, `Delegated task <id> (<title>) [<frozen status>]:` and the result, a failed, interrupted or cancelled task leading with `Error (<code>): <message>`; a result or error is used only when the row is still the revision the cohort froze, so a resend is byte-identical. Results share 16,000 bytes by max-min fair shares: a cut one ends on a char boundary with an open code fence closed and a note to read the rest with `chat_read`, one whose share is under 256 bytes becomes a line saying where to read it, and every task id always appears. A send that answers `request_conflict` or `request_resolved` (a cohort an older binary sent with other text) counts as delivered. Completions join the parent's open cohort; the cohort is sealed and sent only while the parent has no running turn, no background work (`running` without a turn), no pending request, and no turn interrupted in the last two seconds other than by a restart, so completions during a turn merge into one wake and a wake never interrupts or steers. A parent a wake could not reach is owed it: the wake pump (`wake_pump`, started once by the server after recovery and aborted by shutdown) retries owed parents on their session, request and native-operation changes, on chat-list changes, on lag, on a nudge, and on a 30 second sweep that also reseeds them from the store, and drops a local parent that was archived or deleted.

A question (`tool_user_input` request) in a task an agent delegated (`callerScope` is `chat:<parentChatId>`), with `notify` other than `never`, no `parentStopped` and no live `mode: wait` on the task, reaches the parent as one queued message per request (`question_wakes`): `clientMessageId` `chat-orchestration-question:<parent>:<child>:<requestId>`, `delivery: queue`, `origin {kind: orchestrationWake, taskIds, requestIds}`, and a deterministic text with each question's id, prompt and options and how to answer it with `chat_requests` and `chat_respond`. Once the request no longer waits, or the task's monitor ends, the message is cancelled from the parent's queue (`QueueCancel`); a monitor that resumes sweeps stale ones. `launchOptions.inputOwner` is `parent` while every open request is such a question, set without a revision bump before `needs_input`; the parent's `needsInput` attention and the task push then skip it, while the child's own request push and the task's `attention` stay. A result acknowledged before delivery is withdrawn from the cohort. A person's stop of the parent drops both its open and its sealed cohort (see Stop). A sealed cohort is resent after a restart; the stable id makes that idempotent.

A question a child asked before the runtime restarted stays pending as `answerBy: "message"` (see the agent chat runtime [readme](../agent_chat_runtime/readme.md#recovery-and-lifecycle)). Startup reconciliation (`RuntimeStore::recover_chat_orchestration`) leaves a `needs_input` task whose child keeps such a question of its head turn unsettled and lists it in `awaiting_answer`, and the host resumes its monitor. The monitor keeps the task waiting while the question is open even though the head turn ended, routes it to an agent parent as before, and once the answer's turn (a user message with `origin {kind: questionAnswer, answeredTurnId}`) follows the head it moves the head there and follows it to the end. `chatOrchestration.respond` with such an answer moves the head itself and re-arms the child's monitor; a task has at most one monitor at a time.

## Errors

`errorCode` (snake_case) next to `error`: `provider_unavailable`, `background_wait_failed`, `request_conflict`, `chat_not_found`, `task_not_found`, `not_in_lineage`, `mode_ceiling`, `caller_turn_inactive`, `chat_credential_invalid`, `chat_scope_denied`, `chat_archived`, `invalid_target`, `unsupported`, `host_unavailable`, `chat_orchestration_shutdown`.

## Host shutdown

The host calls `ChatOrchestrationService::shutdown().await` before `AgentChatRuntime::shutdown`. Orchestration permanently closes admission, aborts its requests and task monitors, and awaits their cancellation within one five-second deadline. Wake delivery is inline in those jobs and quiesces with them. A `false` result retains unfinished handles for a shutdown retry; the host must leave chat actors running and must not claim disposal until shutdown returns `true`. Completed jobs remove their own handles instead of accumulating task history in memory.

Shutdown does not fail or cancel durable tasks, remove receipts, or acknowledge undelivered wakes. A request stopped during preparation or inference leaves its committed state for startup recovery. A sealed wake keeps its stable message id for replay. Requests arriving after admission closes fail with `chat_orchestration_shutdown` before authorization, target preparation, or runtime effects; ordinary request authorization and receipt behavior remain unchanged while admission is open.

## Remote hosts

The hub owns the ledger and task routing. A satellite owns its chats' providers and transcripts. A chat on a satellite gets its credential from the satellite, which forwards `chatOrchestration.*` from that bound connection to the hub with `originChatId`; the hub accepts it only when that chat's workspace belongs to the forwarding host.
