# Agent Chat Experience Implementation

Status: implementation and integration validation complete; final native acceptance checks are recorded below. This plan executes the [experience analysis](agent-chat-experience-analysis.md); it does not describe already-shipped behavior. Baseline: `2efa844892f9831a00096bd8215ae702ad85333b`.

## Spec

New Agent Chat opens directly into a focused composer. The runtime persists a draft without starting a provider until the first message. Provider and model selection is searchable and atomic, defaults synchronize through the host, and Settings manages provider instances, models, and write-only credentials. Desktop and paired mobile use the same contract and conversation semantics. Existing chats retain cross-provider context handoff. Chat tasks remain separate from terminal orchestration and use Activity as their sole shared attention hub. Background work never changes the selected workspace or tab.

The accepted proposal defaults are host-shared read state and preferences, guarded discard of never-sent chats, explicit default alongside last-used selection, mobile chat/settings controls with launch-definition editing restricted to desktop, and idle-only wake delivery. Native subagent lineage and history operations require truthful capability gating and explicit unsupported results where a provider cannot honor an operation. Draft disposal must preserve unsent text held by another client.

## Design

- Rust runtime and store own processes, lifecycle, provider configuration, revisions, idempotency, credentials, read state, and synchronization. Clients never parse native provider frames to implement application behavior.
- The pure Dart `alera_agent_chat` package owns wire DTOs, selection resolution, searchable catalog grouping, request labels, and repositories. Shared contract additions preserve existing client fakes and capability fallbacks.
- Flutter features own presentational composition and narrow view state. Existing Alera tokens, typography, design-system components, and focus routing remain authoritative.
- Settings mutations use revision checks and caller-scoped receipts. Sensitive values are write-only and use the existing native credential boundary; they never enter catalog responses or change events.
- Native operations are distinct from transcript operations. File rewind must never be presented as conversation rollback, and transcript rewind must explicitly disclose whether filesystem changes were reverted.

## Canonical Contracts

- Provider settings: `agentChat.providerInstances.get`, `upsert`, `remove`, `removalImpact`; write-only `agentChat.secrets.set` and `clear`. Catalog remains `agentChat.providers` and accepts an explicit refresh.
- Preferences: `agentChat.preferences.get` and `update`; update operations use `type` with `setDefaultSelection`, `setProjectDefault`, `setModels`, and `setFavorites`. Remembered selection is host-written after a successful first send.
- Provider-default model: omit `model` on create/send, and use an explicit `model: null` reset on configure. Never serialize the provider-default selection as an empty model id.
- Queue steering: `agentChat.queueSteer {queueId, turnId}` is an atomic actor operation and requires actual native steering support. Queue edit is separate from steering and preserves attachments.
- History: fork, rewind, archived delete, approval history, and turn diff have independent capabilities. A native method being declared does not mean every adapter supports it.
- Events: existing chat changes plus preference/provider changes and explicit chat deletion notifications. Clients subscribe before reading snapshots and refetch after gaps or reconnects.
- Optional operations remain capability gated on desktop, mobile, CLI, and MCP. Additions do not bump the strict runtime protocol version.

## Tests

1. Runtime/store: zero provider spawns during draft creation or pre-send switching; first send starts exactly once; restart preserves drafts; close/send and cancel/start races retain committed messages; retry receipts are stable; migration/reopen is idempotent.
2. Settings: revision conflicts, instance impact, discovered/custom model merge, disabled defaults, cache TTL, bounded probes, caller permissions, and absence of credentials from responses, events, diagnostics, and errors.
3. Native adapters: exact request ids and wire shapes, stale-turn steering guards, fork/revert boundaries, unsupported capabilities, cancellation, and effort validation using scripted transports.
4. Shared Dart: nullable model/default reset, selection precedence, picker search/grouping, hidden-current models, request labels/order, changed/deleted events, and repository payload fidelity.
5. Flutter: direct open and focus without navigation races, searchable keyboard-operable picker, narrow layout, request typing guard, draft preservation, live/failed transcript grammar, retained view state, Settings updates, and explicit task navigation.
6. Final generation: one completed source batch per desktop/mobile package, `build_runner build`, generated-EOF normalization, format, analyze, and relevant tests. No codegen watchers.
7. Integration: runtime and client capability parity, remote-host forwarding, paired-phone permissions, notification deduplication, scoped CLI/MCP documentation, landing keyboard/design fidelity, and performance under sustained output.

## Assumptions and Validation Boundaries

Rust uses the pinned 1.98 toolchain. Dart/Flutter checks use the installed 3.13.2/3.47.2 environment, not the older default shell environment. Shared Cargo builds are serialized to avoid redundant compilation and target-lock contention. UI tests run after final code generation. Mock transport tests do not establish live provider authentication or visual acceptance; those results are reported separately. No production inference, credentials changes, release, or merge is implied by this implementation plan.
