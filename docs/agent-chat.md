# Agent Chat

Agent chats are workbench tabs that talk to a coding agent through the runtime host's provider adapters instead of a terminal. They coexist with terminal tabs. The runtime host owns the provider process and the transcript, so a chat keeps running when the window closes and the same chat is driven from desktop and paired phones.

## Layers

- `packages/alera_agent_chat` (pure Dart, shared with mobile): the `agentChat.*` wire contract, the snapshot and change models, the `AgentChatThread` reducer, the timeline projection and `RuntimeAgentChatRepository` over an `AgentChatTransport`. See its [readme](../packages/alera_agent_chat/readme.md).
- `lib/src/features/agent_chat/infra`: `RuntimeHostAgentChatTransport` adapts the desktop runtime client, mapping host errors to package exceptions and the socket's connect/disconnect events to the package lifecycle events.
- `lib/src/features/agent_chat/application`: `AgentChatController` (one per open chat) reads the snapshot after subscribing to changes, applies changes by cursor, reloads on a skipped cursor, a misaligned text append or a reconnect, and keeps itself alive while a send or a response is in flight. Composer drafts persist locally in desktop SQLite and phone preferences, scoped by host, workspace and chat. Hydration cannot overwrite newer edits. Unanswered submissions retain their original IDs and are restored separately from later composer text.
- `lib/src/features/agent_chat/presentation`: the tab surface, timeline, docks, composer, direct chat entry and archived-chat picker.
- `mobile/lib/src/features/agent_chat`: phone controllers and presentation over the same package, with `MobileAgentChatTransport` adapting the direct or relay runtime connection. The phone never starts a provider process.

The runtime side is described in `rust/alera-cli/src/terminal_host/server/agent_chat_runtime/readme.md`; chat orchestration in [agent-chat-orchestration.md](agent-chat-orchestration.md).

Human CLI/MCP controls, independent capability gates, host Settings, explicit model resets, and retry identities are described in [Agent Chat CLI And MCP](agent-chat-cli.md). The `alera agent-chat` group is distinct from lineage-bound `alera chat` orchestration; Settings tools do not enter the injected agent catalog.

## Workbench integration

- Tab kind `agentChat` with host-owned payload `{chatId, provider, providerInstanceId, model?}`; `agentChatId` is read as a legacy alias. The app declares `supportedTabKinds: ["agentChat"]` in its hello, so older apps never receive these tabs.
- "Agent Chat" in a pane's add-tab menu, the Agent Chat card of an empty side panel, and the New Agent Chat shortcut (`Mod+Shift+T`) open a composer directly. Provider startup is deferred until the first send. The selected provider and model can be changed in the composer; when no enabled provider is available, the draft remains unselected and offers Provider Settings. Creating or reusing a draft focuses it only while the person is still on that workspace.
- Closing a chat that has never sent a message discards its record and tab atomically; otherwise it archives the chat and stops its provider while retaining history. The host guards close/send races. A deletion event lets another client retain its local unsent text. Archived Chats is a separate entry, and Reopen brings a retained chat back in a tab.
- A chat tab shows the status dot colors agent terminals use (working, waiting for the person, failed) even while the chat is not open. The dots come from `agentChat.list` statuses kept current by each chat's session and request changes, not from terminal agent presence.
- The workspace's agent surfaces list every chat tab beside its terminal agents: the sidebar row and its compact summary, the Workspace Details Agents section, the tray and Dock badge, and the phone's workspace rows. Both apps read them from one shared tracker over `agentChat.list` (`AgentChatAttentionTracker`). A chat that another chat delegated to sits right under that chat when both are in the same workspace (`parentChatId` on the list), so several chats in one workspace each keep their own tree. A row reads the chat's own state: a parent waiting on a child that needs input reads as working, and only the child counts as needing the person, so one request is never counted twice. Selecting a chat row opens its tab; a chat closes from its tab rather than from the row.
- Every entry point checks `agentChatV1`. Against an older runtime the menu entry is hidden, the shortcut explains that an update is required, and an existing chat tab shows Update Required. There is no fallback.

## Conversation

- Each turn shows the prompt, compact live work, a "Worked for" divider, then the answer. Commands, edits, tool calls and reasoning expand for details; failed or interrupted work stays visible. A failed turn shows the agent's own reason when it gave one, including an ACP agent's idle error and a failed Grok completion's result. An error an ACP agent reports while no turn runs shows as an error notice, unless it repeats the failure of the turn that just ended. Scroll position and disclosure state are kept per chat, with an explicit Jump To Latest action when the reader leaves the live edge.
- While the agent compacts its context, the live row reads "Compacting for 12s" and ticks each second, on desktop and phone; the compaction stays a timeline row afterwards. Claude reports compaction from its status frames, Codex from its context compaction items. Claude API retries show as one "Provider retry" row that settles as recovered, and a hook that drops the prompt or another non-info Claude notice shows its reason. Foreground Claude Bash commands stream their output while they run, as Codex commands do.
- Approvals, questions and supported elicitation forms share a request dock above the composer. It offers exactly the runtime's decisions, pages through pending requests and retains drafts per request. Focus changes respect recent typing rather than interrupting the composer.
- MCP elicitations from Claude Code and Codex open the same request card: a form shows every field and default and sends what the person entered, a link opens in the browser, and an empty form is a confirmation. Nothing is filled in on the person's behalf. The phone offers Accept only for a confirmation and says when a form cannot be filled in there. A request the agent withdraws, for example because the CLI cancelled it, closes its card. Question options can carry a Markdown preview (`optionPreviews`, from Claude's `AskUserQuestion`): desktop shows it on request under the option, the phone in a sheet, and opening it never answers the question.
- Antigravity's questions open as single-choice question cards rather than approvals; Skip and Stop cancel them.
- The runtime checks question answers before it resolves the request; an answer that names an unknown question, leaves a question blank or picks something that is not an option keeps the question open with an error.
- Stop interrupts the running turn, or with none running stops the background sub-agents earlier turns left, and then cancels every task the chat delegated, with their descendants, so stopped children cannot start the chat again. A steer sent while a stopped turn is still ending waits in the queue instead of being lost.
- A slash command such as `/compact` always reaches the agent as a command: context merged back from a fork or carried over to a new agent session waits for the next message.
- Input that another chat or an orchestration wake sent renders as a notice rather than as the person's message, and never navigates anywhere.
- A notice an ACP agent sends during a turn, such as a model fallback, shows as a notice with its title and description while the reply keeps streaming.
- Find in Chat (`Mod+F` while the focus is anywhere in a desktop chat) opens a find bar over the timeline. It searches the loaded prompts, steers, answers, plans, notices, unsent messages and tool titles and commands, ignoring case, and counts matching rows rather than occurrences ("3 of 12"). Enter and Shift+Enter or the arrows step through them, wrapping; the active row is outlined, scrolled into view, and any fold hiding it (the turn's work, a command group, a long message or plan) opens. Escape closes the bar and returns the focus to where it was. Earlier pages that were not loaded are not searched; the bar says so while Load Earlier Messages is available. The matcher lives in `alera_agent_chat`; the phone does not offer find yet.
- The latest proposed plan of an idle plan-mode chat offers Refine beside Implement Plan. Refine puts the caret in the composer, whose hint asks what to change, and the chat stays in plan mode, so the next message answers the plan rather than implementing it.
- Desktop agent Markdown is rendered without fetching images; `http`, `https` and `mailto` links leave the app. TeX math in `\(…\)`, `\[…\]`, `$…$` and `$$…$$` outside code is typeset in Flutter by the Markdown renderer's bundled `flutter_math_fork`; a single `$` only counts as math when text follows it and the closing `$` is not followed by a letter or digit, so prices and shell variables stay text. Mermaid fences still render as code: the native Mermaid renderer only reads workspace files. Mobile uses the workspace Markdown viewer's remote-image URI policy and opens `http` and `https` links in the browser. Bare file paths open as workspace files on both surfaces.

Long text, reasoning and tool output are stored in bounded continuation rows. The shared timeline joins contiguous rows per stream while preserving the original item IDs used by synchronization. A history page with missing rows shows selectable partial text and a notice; loading the remaining history restores the complete message and its Markdown rendering. Automated partial prompts stay notices and do not enter prompt history.

Large native metadata keeps a redacted preview on its visible item and stores the complete redacted JSON in linked hidden rows. Hidden rows do not appear in normal snapshots, history or timeline changes. Load Full Data fetches that text explicitly through the paged `agentChat.payload` endpoint, including archived chats. Loading checks chunk order and payload consistency before exposing a bounded selectable preview and Copy Full Data. Native JSON is not decoded or pretty-printed on the UI isolate; loading and retry states remain local to the details panel.

## Composer

- New chat entry shows a pending state while the host creates the draft and focuses its composer, including side panels. Moving to another field or surface during creation preserves that focus and selection.
- Enter sends; while a turn runs the runtime queues the message, or steers only when the adapter supports native steering. The queue dock supports cancellation, text editing without losing attachments, and promotion to steering with the exact active turn id. Failed or unsupported steering leaves the queued entry intact. Escape stops a running turn. Arrow keys in an empty composer recall earlier prompts the person sent.
- With `agentChatQueueEditV1`, Edit on a queued message opens it in the chat's own composer under an Editing Queued Message banner, on desktop and phone. The person's draft is set aside (and is what persists meanwhile); Send saves the text through `agentChat.queueEdit`, and Cancel or Escape brings the draft back. Only the text changes: the message keeps its attachments, and files added during the edit return with the draft. If the message leaves the queue first, a changed edit becomes the draft when there was none, otherwise the person's draft wins and a notice says the edit was dropped. Older runtimes take the message back into the composer instead.
- With `agentChatQueueReorderV1`, `agentChat.queueReorder` moves a queued message to a new position, persisted with the queue. Desktop drags a row by its grip or moves the focused row with Alt+Up and Alt+Down; the phone lifts a row with a long press. A queue of more than three collapses behind Expand Queue.
- Desktop chat shortcuts act on the chat that holds the keyboard focus and let the key through when they cannot act: Edit Last Queued Message (`Alt+Up`, from the start of the composer), Steer Next Queued Message (`Mod+Alt+Enter`), Toggle Plan Mode (`Mod+Alt+P`), and Increase or Decrease Reasoning Effort and Stop Agent Turn, which are unbound by default. The queue's Edit and Steer tooltips show their keys.
- A sent message shows immediately and is replaced by the runtime's item carrying the same client message id. A failed send keeps its id, so Retry is deduplicated by the runtime; Edit returns the text to the composer.
- A searchable combined provider/model picker lives in the composer. Provider switches require an idle chat and preserve context. Choosing Provider Default explicitly clears the prior model. An ACP agent whose session lists its models (a model option or a `models` state) switches models between turns in place; a model it refuses reads "The agent did not accept the model". Approval mode, plan mode, verified model-specific reasoning effort and context usage stay alongside the picker. Plan mode is offered for Codex, Claude Code and Cursor; Claude switches its permission mode per turn and its `ExitPlanMode` plan appears as the proposed plan. Plan progress (the agent's task list) comes from Codex plan updates, Claude `TodoWrite`, Cursor, OpenCode todos and ACP plan updates. Full Access requires confirmation. The runtime rejects settings it cannot honor and explains the failure above the composer.
- Claude plan progress also comes from its task tools (`TaskCreate`, `TaskUpdate`, `TaskList`, including those of sub-agents), which update one shared checklist; after a restart Claude's own task store fills it. A checklist the agent emptied disappears. Full Access on Claude runs with approval checks when Claude's settings disable bypass permissions (`auto`, or `default` when auto mode is disabled too), and a notice says so once.
- ACP agents that send `usage_update` fill the Context Window bar too.
- Context usage fills a Context Window bar against the model's window, in the desktop usage popover and the phone's usage sheet. When the provider reports where it compacts on its own (Claude with `CLAUDE_CODE_AUTO_COMPACT_WINDOW` set), a tick marks that point with "Compacts automatically at about N tokens." Codex reports its live context from token ticks and Claude from its assistant frames. A rejected rate limit shows as a full window with its reset time, and a window keeps its last report until the provider reports it again.
- `@` at the start of a word opens a menu of workspace files from the Quick Open index; picking one attaches it and removes the `@` token. The desktop attaches the absolute path, as a drag from Explorer does; the phone attaches the workspace-relative path as a Workspace File, as the Add Attachment sheet does, and treats `@` as plain text when the host serves no Quick Open (`mobileCodexWorkspaceFilesV1`). `/` as the first character of the prompt opens commands: `/model` opens the picker, `/plan` and `/default` switch the interaction mode when the agent has a plan mode, and `/usage` opens the usage popover or sheet. After them come the agent's own commands (`session.commands`: ACP `availableCommands`, Claude Code's commands, Pi's), each with its description or input hint, and then its skills as `/skill:name`; picking a command replaces the token with `/name ` for the person to finish and send, because the agent expands it. A local name always wins over an agent command of the same name, even while the local command is hidden, and a skill hides an agent command of its name. `/` opens at any word start that is not a path, as in T3 Code, but agent commands are only offered at the start of the prompt, where agents expand them; the menu ranks matches with T3 Code's search ranking. A command that cannot run stays listed with its reason. On desktop, Up, Down, Enter, Tab and Escape drive the menu while it is open, before history, send and stop; the phone shows the suggestions above its composer, picks on tap and dismisses with Close. The trigger rules, the debounced file search and the merged command list live in `alera_agent_chat`, shared by both clients.
- With `agentChatSkillsV1`, a currency sigil (`$`, `€`, ...) at a word start opens the agent's skills from `agentChat.skills`, unless what follows is an amount such as `$5` or `$10k`. Rows show the skill's display name and short description; agent-only and disabled skills are hidden. Picking one inserts `$name `, which the runtime adapter turns into the provider's own invocation when the prompt is sent. Finished mentions of known skills are painted in the composer field, and sent messages draw them as chips. An agent that reports skills only from a running session (ACP registry agents, Pi) says so until its first message. Without the capability `$` stays text. The skill inventory and per-provider details are in [Agent Chat Harness Parity](agent-chat-harness-parity.md).
- With `agentChatGoalV1`, Codex chats offer `/goal`: an objective sets a goal Codex keeps working toward across turns, and `show`, `pause`, `resume` and `clear` manage it. A banner above the composer, on desktop and phone, shows the goal's status, token and time spend and objective, with Resume (hidden while a turn runs) and Clear, which send `/goal resume` and `/goal clear`. Turns Codex starts on its own for the goal run as ordinary turns marked "Continuing toward the goal", with Working shown, messages queued behind them and Stop pausing the goal. A goal command sent over a running turn never steers; one that starts or ends goal work goes first in the queue and stops the turn.
- Narrow composers shorten the provider-default label to Default and fold secondary controls into More Controls. Active Full Access and Plan remain visible as warning/mode indicators; model labels truncate with their complete value available in the tooltip.
- A dropped connection keeps the transcript readable, disables the composer and reloads the snapshot when the runtime returns. A stopped session offers the recovery actions the runtime verified (resume or start a new session); sending also resumes it.

## Providers and Models

Settings manages provider instances for the selected host, including enabled state, executable and arguments, environment overrides, custom models, defaults, hidden models and favorites. Grok, Antigravity and ACP agents receive the custom models and the default model at launch, so the agent is asked for them even when its session does not list them. Sensitive environment and option values are write-only; responses expose only whether a secret is saved. Mutations use revisions and request receipts. An Antigravity instance whose ACP runtime (`agy_acp_server`) is missing says so and that the Antigravity app, IDE and `agy` CLI are separate installations. Catalog status distinguishes installation, bounded discovery and verified sign-in evidence rather than treating an existing credential as proof of authentication. As in T3 Code, Pi's status explains a default model it cannot start: it compares `pi --list-models` with the default from Pi's launch arguments or global `settings.json`, and on Pi 0.84.1 or later, unless the launch arguments pass `--api-key`, asks `pi auth check --provider <provider> --json --no-refresh` whether credentials are missing. The explanation is the status detail rather than a sign-in failure, because Pi's other models still work.
A Claude Code instance whose effective `ANTHROPIC_BASE_URL` (Claude settings `env`, then the instance and login environment) points at a non-Anthropic http(s) host reads as signed in through a Custom API endpoint, because Anthropic account fields cannot verify proxy credentials. A Claude chat whose earlier session never saved a message starts a new session that continues the chat, with a notice. A Codex exit error quotes the stderr line that explains it.

New-chat selection resolves project defaults, the launching chat in the same workspace, an explicit default, remembered selection and finally the first enabled available instance. Preferences synchronize through the host. Paired phones can change preferences, model visibility, enabled state and secrets; launch definitions remain desktop administration. Verified installation and sign-in suppress redundant Install and Sign In actions. An ACP instance without an executable shows Setup Required rather than a launch error. Sign In, Install and Update use an opaque provider-instance/action request: the owning host selects its verified recipe and hydrates the instance environment before spawning a command terminal. Secrets and launch recipes are never typed by the client. A desktop can run these actions on a Remote Host when both runtimes advertise `agentChatRemoteProviderSetupV1`; older hosts retain the copy-only explanation. The phone retains copy-only setup. Remote setup output and input are restricted to admitted desktop clients, and the ephemeral terminal is closed with its dialog.

## Attachments and Attention Push

`agentChatAttachmentUploadV1` transfers selected local files to the chat's owning host through bounded, replayable chunks. Uploads are scoped to the authenticated human, workspace and chat. A completed upload returns an attachment receipt; send resolves that receipt on the owner instead of trusting a client path. Desktop transfers device-picked or pasted files before sending; workspace references remain owner-host paths and are never guessed from matching local files. Phones can upload photos and files directly through their paired hub to a remote chat owner. Unsupported remote uploads fail explicitly; older local hosts retain their existing path/upload flow.
Providers advertise which attachments they take (`capabilities.images`, `capabilities.files`), and both apps offer only those: desktop disables Add Files for a provider without attachments, and the phone's sheet hides the sources the provider cannot take. Every local attachment also reaches the agent as a `[Attached file "name" is saved at: path]` line, so an agent reads a file it cannot take natively with its own tools. Codex takes images natively; Claude Code takes PNG, JPEG, GIF and WEBP images and countable PDFs natively within its 28 MiB and 100-page session budget.
With `agentChatGeneratedImagesV1`, an image Codex generated shows under its Generated image row once it is saved: the runtime reads only the path the item recorded, checks it is a PNG, JPEG, GIF or WEBP file of at most 16 MiB and serves it in 256 KiB pieces through `agentChat.generatedImage`. Clicking it opens the file on desktop; the phone opens it full screen. The turn waits until its images render before it completes.

Unanswered submissions retain completed attachment receipts and the same client message ID, so retry does not silently upload or execute a different prompt. Upload errors keep the submission available for Retry or Edit. Unused uploads expire; referenced files remain with their chat history. Device-local drafts are not synchronized between clients.

With runtime cloud push enabled and the phone subscribed to Attention, newly committed approval/question requests and Chat Tasks needing attention produce identifier-only notifications. Cursor replay, request/task overlap and cooldown repeats are damped; snapshots do not trigger notifications. Remote chat events use the hub's cloud account after owner validation. Tapping opens the matching chat or Activity task; arrival and foreground notices never navigate automatically. Tests use fake cloud delivery and do not prove FCM delivery to a real phone.

## History and File Checkpoints

Fork, transcript rewind, native conversation rewind, file rewind, approval history and turn diff are independent capability-gated operations. Transcript rewind restores the prompt and retained history without reverting files. Native conversation rewind requires an exact supported provider boundary from the current process; the host does not retry a count-based rollback as an approximation.

Claude File Checkpointing can be enabled while idle and takes effect on the next provider start. Rewind Files uses only a provider-observed user-message UUID. Provider acknowledgment and observed file effects are separate result fields; missing evidence is presented as unverified.

Native rewinds reserve a durable intent before provider I/O and finalize history and receipts atomically. An interrupted or ambiguous operation pauses mutations and exposes explicit reconciliation actions. Restart recovery never blindly repeats native I/O. Both clients preserve the draft while the operation is unresolved.

## Chat Tasks and Attention

Chats can send messages to existing chats or delegate work into an existing workspace, a shared workspace or an isolated worktree in another project. The task dock preserves parent/child context and keeps navigation explicit. Settled plans can open Implement In New Workspace using the same delegation form. Human callers can attach a parent chat; injected agents remain bound to host-validated lineage and generation credentials. Activity remains the common attention surface for Chat Tasks, Runs, Questions and Automations.

Read cursors are host-shared. Task and waiting-input notices do not change the selected workspace or tab.

A chat whose running turn only waits on its delegated tasks (every tool call still in progress is `chat_task_wait` or a `chat_delegate` with `mode: wait`, under any provider's naming of the Alera tools) reads as Waiting on delegated tasks instead of Working: on the tab dot, in workspace rows and on the phone. Such a wait never raises a "finished" notice, which follows the turn itself. After a fresh start or reconnect, a chat already waiting reads as Working until its next tool change. The task dock's collapsed line names a single open task (`Running X`, `Waiting on X` or `X needs input`) and counts several (`Running 3 tasks` or `Waiting on 3 tasks`, with the counts) next to the newest open task's title; it says Waiting when the chat is blocked on a wait, or idle while tasks that will wake it run. A question a delegated task routed to its agent parent does not raise the parent's needs-input state; its wake reads "A delegated task asked a question" and claims no outcome. An `alera-chat://` link in a message opens that chat on its tab.

Provider-native sub-agents are separate from application-owned chat tasks. The runtime links a sub-agent's items to the tool call that started it (`normalized.parentItemId`) and folds the provider's task events into that call's `normalized.subagent` (`status`, `description`, `summary`, `taskId`, `taskType`). Claude's Task tool links through `parent_tool_use_id` and its task notifications; Codex collab calls link through the child threads they name, whose events report the sub-agent's state. Both apps show each sub-agent under its call as a Sub-agent row with its state, step count and final summary; when the provider streams the sub-agent's own items (Claude), they sit under that row along a thread line instead of mixing into the main agent's answer. Codex streams the child thread's own items under the collab call the same way. With `agentChatSubagentThreadsV1`, a sub-agent row opens the sub-agent on its own, read-only, with a sub-agent bar in place of the composer (model, effort, a live status timer, Open Parent), and a running sub-agent stops on its own where the provider supports it (Claude, Codex). A Lineage control (desktop) and sheet (phone, from the tab's actions) list the parent chat, the fork source, forks, delegated chats and sub-agents; a fork merges back into its source with `agentChatMergeBackV1`. See [Sub-agent Threads And Chat Relationships](agent-chat-subagent-threads.md). With `agentChatWorkflowsV1`, a Claude Code workflow (`local_workflow`) is a sub-agent row named after its script that unfolds its phases and members; the opened workflow shows its usage, its script and each member's prompt and answer, and stops like any sub-agent. With `agentChatTransfersV1`, context moved into a chat (a fork's history, a merge-back, a provider handoff, a delegated brief or result) is recorded in that chat and shown as timeline and lineage rows, and chats, sub-agents and transfers preview in hover cards on desktop and on a long press on the phone; see [Hover Cards And Context Transfers](agent-chat-harness-parity.md#hover-cards-and-context-transfers). Providers that report no sub-agents keep their calls as ordinary rows.

## Known limits

- Uploads require the owning host's attachment capability; there is no remote path fallback for a device-local file.
- Reasoning effort is shown only for verified provider/model metadata; an adapter API alone does not fabricate available values. Antigravity lists its models and each model's thinking levels from a short-lived ACP session, probed once at a time per instance, kept for 30 minutes and given 90 seconds even when the catalog stops waiting after 15; a failed probe is dropped so the next catalog request probes again. The chosen thinking level is written after the model at start and before each turn.
- Unification with terminal orchestration remains a separate follow-up.
