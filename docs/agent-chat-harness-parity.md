# Agent Chat Harness Parity

This page inventories what T3 Code (`reference_projects/t3code`, read at `origin/main`) offers around agent harnesses: skills, slash commands, plugins, apps and connectors, MCP server status and the surfaces next to them. For each item it records the providers, the native source, how the item is listed and invoked, how the composer and timeline draw it, management actions, refresh, mobile parity and what Alera does. Items Alera does not implement say exactly why.

Sub-agent threads, the relationships control and merge-back are inventoried in [Sub-agent Threads And Chat Relationships](agent-chat-subagent-threads.md).

## How Alera Serves Skills

- Protocol: `ProviderSkill` (T3's `ServerProviderSkill`), the `session.skills.updated` event, the shared mention grammar (`skill_mentions`, `rewrite_skill_mentions`, `dollar_skill_mentions`, `leading_skill_mention`), the frontmatter reader and the skill name order live in `alera-provider-protocol`.
- Runtime: `agentChat.skills` behind `agentChatSkillsV1` (control file, `status.get`, `mobile.hello`; allowed for phones). A live session's report wins and stays in the actor's memory, never in the snapshot; otherwise the factory discovers per instance and cwd, cached for five minutes. Answers carry `status: ready | pending | failed`. See the runtime [readme](../rust/alera-cli/src/terminal_host/server/agent_chat_runtime/readme.md).
- Clients: `alera_agent_chat` holds the model, the `$` trigger (a currency sigil at a word start unless it is an amount), T3's search ranking, the merged `/` menu and `AgentChatSkillsLoader`. Desktop and phone list skills in the composer menu, insert `$name `, paint finished mentions of known skills in the field and draw them as `AleraInlineChip` chips in sent messages. A runtime without the capability leaves `$` as text.
- Invocation stays in the adapters, so a skill typed through the CLI or an MCP client (`alera agent-chat send`) is invoked the same way. T3 exposes no skill, plugin or MCP listing to agents or CLI users, so Alera adds no CLI verb or MCP tool for them.

## Differences From T3 Code

- The composer field keeps `$name` as text and paints it, because a Flutter text field cannot hold T3's collapsed chip; the sent text is identical.
- Skill names containing white space are dropped (`ProviderSkill::from_native`); they cannot be typed as one mention token anyway.
- `localeCompare` ordering is approximated by the ICU root order for the ASCII names skills use (`compare_skill_names`, `agentChatLocaleCompare`).

## Codex Feedback

- Flow: the Codex adapter lists `/feedback` next to `/compact`. When the person sends `/feedback` or `/feedback <reason>` with no attachments, desktop and phone take the send instead of starting a turn, as T3 Code's `useComposerSend` does. A chat with no message yet answers T3 Code's guard, `Send a message before you submit feedback.`, and keeps the draft. One upload per chat runs at a time; another `/feedback` while it runs does nothing.
- Consent, unlike T3 Code: before anything leaves the machine, an `AleraConfirmDialog` (Send Feedback to OpenAI?) says that the conversation thread and the Codex logs are uploaded to OpenAI, and repeats the reason. Cancel keeps the draft; Send Feedback clears it and uploads.
- Wire: `agentChat.feedback {requestId, chatId, reason?}` behind `agentChatFeedbackV1` (control file, `status.get`, `MOBILE_HELLO_CAPABILITIES`, phone allowlist). The runtime calls `Provider::upload_feedback`; only Codex implements it, others answer `unsupported`. The answer is `{feedbackId}`, and the request id makes a retry replay the receipt instead of uploading twice. A runtime without the capability never offers the command, and its text goes to the agent as before.
- Result: a notice above the composer shows uploading, then `Feedback sent to OpenAI` with the thread id and Copy ID, or `Could not send feedback to OpenAI` with the reason; sent and failed notices can be dismissed. T3 Code keeps submissions on the client and so does Alera, in a per-chat store that outlives the tab for the app session: the upload does not change the conversation, so writing it into the runtime transcript would put it into every later snapshot, handoff and fork of the chat for no agent-facing reason.
- Differences: the runtime refuses an upload while a turn runs (`turnActive`), because the provider call holds the chat's actor as `/compact` does and a running turn's events would wait behind it; T3 Code uploads during a turn. A chat whose provider is not running (after a runtime restart) answers T3 Code's `Send a message first.` T3 Code's web client also anchors the command and the result as local rows in the timeline; Alera shows the notice only, as T3 Code's phone does. The Codex adapter refuses a turn whose whole text is `/feedback`, so an older client that sends the command as text never reaches the model.

## Not Implemented

- **MCP Apps.** They render a provider-supplied HTML resource in a sandboxed frame (`sandbox="allow-scripts allow-forms"`, opaque origin, document CSP from the app's `_meta.ui.csp`) and run a JSON-RPC bridge (`ui/initialize`, `tools/call`, `resources/read`, `ui/message`, `ui/open-link`, display modes). Alera ships no web view on desktop (Linux, Windows, macOS) or on the phone, so there is no sandbox to host untrusted HTML; drawing it any other way would execute nothing or bypass the sandbox. Porting needs a vetted web view dependency on every platform first.
- **The Show Skills In Slash Menu toggle** and **Find in Chat over chip labels**, as listed above.
