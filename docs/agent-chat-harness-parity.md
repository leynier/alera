# Agent Chat Harness Parity

This page inventories what T3 Code (`reference_projects/t3code`, read at `origin/main`) offers around agent harnesses: skills, slash commands, plugins, apps and connectors, MCP server status and the surfaces next to them. For each item it records the providers, the native source, how the item is listed and invoked, how the composer and timeline draw it, management actions, refresh, mobile parity and what Alera does. Items Alera does not implement say exactly why.

Sub-agent threads, the relationships control and merge-back are inventoried in [Sub-agent Threads And Chat Relationships](agent-chat-subagent-threads.md).

## ACP Native Child Sessions

T3 Code (`6958838214` in `provider-acp`, enabled for Claude Agent by `b1167b6ca2` in `provider-acp-registry`) projects the sub-agents Claude Agent runs as ACP child sessions. Only Claude Agent (registry `claude-acp`, or a local `claude-agent-acp` command) reports them; Grok, Antigravity, Devin and Copilot sub-agents stay tool-based in both apps. Alera implements it behind `agentChatAcpChildSessionsV1` (control file, `status.get`, `mobile.hello`).

| Item | T3 Code | Alera |
| --- | --- | --- |
| Detection and negotiation | Launches Claude Agent with `CLAUDE_AGENT_ACP_EXPERIMENTAL_V2=1` unless the instance environment sets it; follows agent work state only when `initialize` answers protocol version 2 | Same (`AcpRegistryAgentFlavor::ClaudeAgent`, `AcpRegistryProviderConfig::launch_env`, which also leaves a host-environment value alone). The ACP adapter's `native_child_sessions` takes effect only on ACP v2; every other agent, and Claude Agent on v1, keeps today's lifecycle. |
| Work state | The prompt response only accepts the prompt; the root `state_update` idle ends the turn; an idle before acceptance is stale | Same. A failed root turn with working children says `childTurnsContinue`, and its message comes from `error.message`. |
| Linking a child | `subagent_update` on the parent names the child and its state; `session_message` on the child names the delegating Agent/Task (or SendMessage) tool-use id; frames before the link are buffered (256) and unrelated or unlinked children ignored | Same, keyed by the delegating call's native item id. The child becomes `task.started` (`awaited`) and `task.completed` events whose `nativeTask.nativeToolCallId` is the Agent call, so the call's `normalized.subagent` carries status, description, model and the child's last answer as `summary`. A child of a child nests under its own Agent call (`parentTaskId`). |
| Child transcript | Tools, messages and reasoning projected into the child thread; usage and titles on the child thread | Items and deltas stream as session items under the Agent call (`parentToolUseId`), ids scoped by child session, so `agentChat.subagent` reads them and desktop and phone open them as other sub-agents. Child usage, titles, plans and commands are dropped: Alera has no per-sub-agent usage. |
| Status | Running, completed, failed, cancelled from `subagent_update` and the child's own `state_update`; a parent waits for working descendants | Same states (`cancelled` reads as Stopped). Each descendant is its own awaited task, so the chat keeps working until all end. |
| Resume | A later delegation (SendMessage) runs the child again with its prompt in the child thread; output after the parent run ended is buffered and a continuation run adopts Claude's own wake (`state_update` running with no prompt) | A later delegation shows its prompt as a user message under the call and restarts the sub-agent's clock. Output after the parent turn ended lands in the call's turn directly. Claude's own wake becomes a turn with `origin: backgroundContinuation` and no user message, marked "Continuing after background work" on desktop and phone. |

| Provisional Agent calls | An Agent/Task call without a prompt is deferred so it never shows twice | Not needed: Alera keeps the call as the sub-agent's own row, so it never duplicates. |

## How Alera Serves Skills

- Protocol: `ProviderSkill` (T3's `ServerProviderSkill`), the `session.skills.updated` event, the shared mention grammar (`skill_mentions`, `rewrite_skill_mentions`, `dollar_skill_mentions`, `leading_skill_mention`), the frontmatter reader and the skill name order live in `alera-provider-protocol`.
- Runtime: `agentChat.skills` behind `agentChatSkillsV1` (control file, `status.get`, `mobile.hello`; allowed for phones). A live session's report wins and stays in the actor's memory, never in the snapshot; otherwise the factory discovers per instance and cwd, cached for five minutes. Answers carry `status: ready | pending | failed`. See the runtime [readme](../rust/alera-cli/src/terminal_host/server/agent_chat_runtime/readme.md).
- Clients: `alera_agent_chat` holds the model, the `$` trigger (a currency sigil at a word start unless it is an amount), T3's search ranking, the merged `/` menu and `AgentChatSkillsLoader`. Desktop and phone list skills in the composer menu, insert `$name `, paint finished mentions of known skills in the field and draw them as `AleraInlineChip` chips in sent messages. A runtime without the capability leaves `$` as text.
- Invocation stays in the adapters, so a skill typed through the CLI or an MCP client (`alera agent-chat send`) is invoked the same way. T3 exposes no skill, plugin or MCP listing to agents or CLI users, so Alera adds no CLI verb or MCP tool for them.

## Differences From T3 Code

- The composer field keeps `$name` as text and paints it, because a Flutter text field cannot hold T3's collapsed chip; the sent text is identical.
- Skill names containing white space are dropped (`ProviderSkill::from_native`); they cannot be typed as one mention token anyway.
- `localeCompare` ordering is approximated by the ICU root order for the ASCII names skills use (`compare_skill_names`, `agentChatLocaleCompare`).

## Codex Feedback

- Flow: the Codex adapter lists `/feedback` next to `/compact`. When the person sends `/feedback` or `/feedback <reason>` with no attachments, desktop and phone take the send instead of starting a turn, as T3 Code's `useComposerSend` does. A chat with no message yet answers T3 Code's guard, `Send a message before you submit feedback.`, and keeps the draft. One upload per chat runs at a time; another `/feedback` while it runs does nothing.
- Consent, unlike T3 Code: before anything leaves the machine, an `AleraConfirmDialog` (Send Feedback to OpenAI?) says that the conversation thread and the Codex logs are uploaded to OpenAI, and repeats the reason. Cancel keeps the draft; Send Feedback clears it and uploads.
- Wire: `agentChat.feedback {requestId, chatId, reason?}` behind `agentChatFeedbackV1` (control file, `status.get`, `MOBILE_HELLO_CAPABILITIES`, phone allowlist). The runtime calls `Provider::upload_feedback`; only Codex implements it, others answer `unsupported`. The answer is `{feedbackId}`, and the request id makes a retry replay the receipt instead of uploading twice. A runtime without the capability never offers the command, and its text goes to the agent as before.
- Result: a notice above the composer shows uploading, then `Feedback sent to OpenAI` with the thread id and Copy ID, or `Could not send feedback to OpenAI` with the reason; sent and failed notices can be dismissed. T3 Code keeps submissions on the client and so does Alera, in a per-chat store that outlives the tab for the app session: the upload does not change the conversation, so writing it into the runtime transcript would put it into every later snapshot, handoff and fork of the chat for no agent-facing reason.
- Differences: the runtime refuses an upload while a turn runs (`turnActive`), because the provider call holds the chat's actor as `/compact` does and a running turn's events would wait behind it; T3 Code uploads during a turn. A chat whose provider is not running (after a runtime restart) answers T3 Code's `Send a message first.` T3 Code's web client also anchors the command and the result as local rows in the timeline; Alera shows the notice only, as T3 Code's phone does. The Codex adapter refuses a turn whose whole text is `/feedback`, so an older client that sends the command as text never reaches the model.

T3 Code previews threads in hover cards and records context moved between threads as `contextTransfers`. Alera ports both behind `agentChatTransfersV1`; the runtime contract is in the runtime [readme](../rust/alera-cli/src/terminal_host/server/agent_chat_runtime/readme.md#context-transfers).

### Context transfers

| `kind` (T3 type) | Recorded in | Timeline row | Lineage row | `chat_transfers` |
| --- | --- | --- | --- | --- |
| `fork` (`fork`) | The fork, at `agentChat.fork` | "Forked From" the source, after the turn it was taken through | Yes | Yes |
| `mergeBack` (`merge_back`) | The source chat, at `agentChat.mergeBack`; `pending` until the next turn carries it, then `consumed` | "Merged Back From" the fork, in place of the merge-back notice; the merged work folds under it | Yes | Yes |
| `providerHandoff` (`provider_handoff`) | The chat itself, at a turn that carries the transcript into a fresh provider session; settles with the handoff marker | The existing Context Handoff divider; no second row | No: T3 skips transfers within one thread | Yes |
| `subagentSpawn` (`subagent_spawn`) | A delegated chat, when the brief's turn starts | "Delegated By" the parent, before that turn | Yes | Yes |

Each row opens its source chat on click and previews it on hover or long press. The records ride in the snapshot and in deltas as `contextTransfers`, so a runtime restart keeps them. `chatOrchestration.transfers {chatId?}`, the injected `chat_transfers` tool and `alera chat transfers` list them, as T3's `t3_thread_transfers` does, with `{transferId, kind, sourceChatId, targetChatId, status}` plus title, task and timing. T3's `resolution` (native fork versus portable context), `basePoint` and `superseded` status have no counterpart: Alera forks by copying the transcript and delivers every pending merge-back instead of superseding older ones.

## Not Implemented

- **MCP Apps.** They render a provider-supplied HTML resource in a sandboxed frame (`sandbox="allow-scripts allow-forms"`, opaque origin, document CSP from the app's `_meta.ui.csp`) and run a JSON-RPC bridge (`ui/initialize`, `tools/call`, `resources/read`, `ui/message`, `ui/open-link`, display modes). Alera ships no web view on desktop (Linux, Windows, macOS) or on the phone, so there is no sandbox to host untrusted HTML; drawing it any other way would execute nothing or bypass the sandbox. Porting needs a vetted web view dependency on every platform first.
- **The Show Skills In Slash Menu toggle** and **Find in Chat over chip labels**, as listed above.
- **Pull request link previews.** T3 fetches a pull request's detail by URL through its server (`pullRequestEnvironment.preview`) and wraps each Markdown link in a preview card. Alera's forge clients look reviews up per workspace checkout and remote identity, not by an arbitrary URL, and the chat Markdown renders links as text spans with no per-link widget, so a card needs both a URL lookup in the runtime and a link widget hook in the renderer. Links keep opening in the browser.
