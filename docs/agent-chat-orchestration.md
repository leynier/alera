# Chat orchestration

## Scope

The runtime owns orchestration between agent chats, including chats in different projects and on connected hosts. This system is separate from terminal orchestration. It uses the same chat actors, persistence, provider sessions, approvals and synchronization as `agentChat.*`. Desktop and paired mobile expose the same human controls. Neither delegation nor messages change the user's selected workspace or tab.

Delegation always names its target: an existing chat, a new chat in an existing workspace, or a new workspace with `mode: worktree|shared`. New workspaces name their project and host explicitly and go through the existing managed/shared workspace API. A child receives the supplied brief only, without copying its parent's history. Provider switches keep chat identity and lineage while changing native session generation.

## Contract

The additive capability is `chatOrchestrationV1`. Host verbs use `chatOrchestration.*`; MCP tools use the `chat_` prefix so they cannot collide with terminal tools. The verbs are `capabilities`, `delegate`, `send`, `task`, `tasks.list`, `wait`, `cancel`, `interrupt`, `backgroundWait`, `requests`, `respond`, `configure`, `updateTitle`, `requestSecret`, `readSecret`, `linkPullRequest`, `unlinkPullRequest`, `listPullRequests`, `watchPullRequest`, `unwatchPullRequest`, `scheduleTask`, `listScheduledTasks`, `deleteScheduledTask`, `runScheduledTaskNow`, `read` and `list`. The CLI group is `alera chat`. Receipt-backed mutations (`delegate`, `send`, `cancel`, `interrupt`, `respond`, `configure` and `updateTitle`) carry `requestId`; MCP exposes `clientRequestId` and maps it to that field. A task acknowledgement with an explicit request ID also uses a durable receipt; legacy no-ID acknowledgement remains compatible. Pure task reads never acknowledge.

`delegate` accepts `{task, title?, role?, notify?, mode: async|wait, waitSeconds?, requestId, agent?: {providerInstanceId?, model?, options?}, runtimeMode?, interactionMode?, target}`. A target is exactly one of `{chat:{chatId}}`, `{workspace:{workspaceId}}` or `{newWorkspace:{projectId,hostId,mode:worktree|shared,branch?,sourceBranch?,reuseExistingBranch?,name?,parentWorkspaceId?,setup:inline|deferred}}`. Worktree targets require `branch`; setup defaults to `inline`. Its response includes `{taskId,chatId?,workspaceId?,status,result?}`.

`send` accepts `{chatId,message,delivery:auto|queue,expectReply,requestId}`. With `expectReply`, it creates a message task whose completion can notify the sender. `task` reads and optionally acknowledges a result; `wait` waits for at most 50 seconds. A bound agent whose running task will wake it gets `next` beside the task from `delegate`, `task` and a timed-out `wait`: end the turn instead of waiting on the task or polling it. Terminal and CLI callers are never woken, so they keep waiting with repeated calls. `tasks.list` includes lineage, target, status, attention and result delivery state. A bound agent that names no `parentChatId`, `childChatId` or `rootTaskId` lists only its own chat's delegations, because several chats in one workspace each own theirs; naming another lineage still reads it, marked `readOnly`. `read` exposes user and assistant text and canonical plans, without provider credentials or hidden reasoning. The event `chatOrchestrationChanged {taskId,parentChatId?,childChatId?,workspaceId?}` invalidates lists on desktop and mobile.

`configure` preserves omitted model and reasoning effort. Explicit null resets either to its provider default. CLI `--reset-model` and `--reset-reasoning-effort` and bound MCP `resetModel:true` and `resetReasoningEffort:true` express these resets without an empty identifier. Settings administration and direct lifecycle/history operations use the separate [Agent Chat CLI And MCP](agent-chat-cli.md) surface and remain absent from injected chat credentials.

Tasks have app-owned `taskId` distinct from `childChatId`, and states `preparing|running|needs_input|completed|failed|interrupted|cancel_requested|cancelled`. Completion follows the child's settled turn, not request acknowledgement. The result is the main agent's last non-blank assistant message, never a native sub-agent's, bounded. A completed turn does not settle a task while the child still works: background work or a native sub-agent the agent resumes from, an open request, a queued message, or tasks the child delegated that will wake it. A continuation turn (a background continuation, a goal continuation, or a wake from a sub-agent or delegated task) moves the task along, and the task settles from its last turn after the child stays quiet for half a second, with the newest answer across those turns. Open child requests produce `needs_input`. Follow-up work produces a new task even when reusing a child chat: a turn the child starts after its task settled, on its own, from a wake, from a person's message or from its parent's own untracked message, opens a `followup` task (`followupOf` names the task it continues) whose settle wakes the parent again.

Human delegate/send requests can explicitly name `parentChatId` (`alera chat --parent-chat-id` on those actions), binding task and wake delivery to their originating chat. This field does not impersonate a bound agent or replace host-derived caller identity. Bound callers retain their credentialed parent and lineage restrictions; their injected MCP surface does not offer human parent selection.

## Human CLI And Public MCP

`alera chat --json human <operation>` accepts an exact structured body through `--payload`, `--payload-file`, or `--payload-stdin`. It refuses chat-bound credentials before dispatch, rather than replacing them. Public MCP tools call this human route and remain absent from the injected catalog. Caller identity comes from the existing host handshake and MCP origin, not a fabricated agent token.

| Public tool | Access | Explicit operations |
| --- | --- | --- |
| `chat_task_query` | Read | `capabilities`, `list`, `read`, `task`, `task-list`, `wait`, `requests` |
| `chat_task_delegate` | Execute | `delegate` |
| `chat_task_send` | Execute | `send` |
| `chat_task_control` | Execute | `acknowledge`, `cancel`, `interrupt`, `respond`, `configure` |

Each tool uses `{operation,payload}` and rejects fields outside the selected operation's canonical body. Mutable tools map their separate `clientRequestId` to `requestId`, including receipt-backed acknowledgement on updated hosts. The legacy CLI and injected acknowledgement path preserves omission when no ID is supplied; supplied IDs remain unchanged. The injected mixed status/acknowledge tool advertises execute access because it can mutate, while public task query remains read-only. The control access class matches existing public task cancellation, terminal interruption, and per-chat execution. Provider/global Settings and secret management continue to require their separate admin tools.

Read/task-list pages default to 100 and accept limits from 1; a limit above 200 reads 200. Task-list uses the returned nonnegative cursor. Query never acknowledges results. Wait accepts 1 to 200 IDs and at least 1 second, defaulting to 50 and `until:all`; a longer wait waits 50 seconds, and a timeout does not cancel work. `null` for an optional field is the same as leaving it out; identifiers, revisions and cursors stay strict. Task/message text is capped at 64 KiB and the body at 256 KiB. Requests require `chatId` or `taskId`. The MCP schemas list exact target, agent, policy, and operation bodies, with no arbitrary provider-option escape hatch.

Human parent binding requires `chatOrchestrationPersonParentV1` on delegate/send; task-list parent filtering is just a query. Delegation effort belongs only in `agent.options.reasoningEffort`, a nonempty string of at most 128 bytes. It and configure effort selection/reset require the independent `chatOrchestrationEffortV1` plus verified destination-model support. Default selection omits model/effort; configure alone accepts explicit null resets. Unknown provider options and credentials are rejected. The ordinary `alera chat` commands share these additive capability checks while retaining their bound lineage route.

## Background work

A chat stays working after its turn while native work the agent resumes from is open: native sub-agents, and background commands the agent marked. `backgroundWait {taskIds, waiting?}` (MCP `chat_background_wait`, CLI `alera chat background-wait`) marks or unmarks the bound caller's own background commands, resolved from its credential, and answers `{matched, unmatched}`; only Claude supports it, and other providers answer an invalid request. When the injected server is present, the Claude system prompt tells the agent when to call it, because Claude Code defers MCP tools behind ToolSearch.

Codex does not resume a parent whose turn already completed when one of its direct sub-agents finishes. The runtime then starts a parent turn itself, an automated message with `origin {kind: subagentWake}` that carries the sub-agent's outcome and final answer, but only while nothing runs, waits or is queued; otherwise the next turn reads the result natively. Claude resumes its own agent and needs no wake.

## Notifications and cancellation

`notify` is `always|settled_only|never`. Async defaults to `always`; bounded waits avoid duplicate notifications and enable a later wake after timeout. Only a settle owes a wake. Parent wakes are durable, idempotent queued messages with a stable client message ID and an increasing delivery generation. Concurrent completions merge into a cohort. A wake names every task with its status and inlines each settled result, failures leading with their error; the results share a 16,000-byte budget fairly, a cut result says to read the rest with `chat_read`, and one whose share is too small says only where to read it. A wake never interrupts a running parent turn: it waits while the parent runs a turn, has background work, has an open request, or was stopped in the last two seconds, and the runtime delivers it once the parent goes idle, including after a restart.

A child's question (`tool_user_input`) in a task an agent delegated reaches that agent as one queued message per request, with the question, its options and how to answer it with `chat_requests` and `chat_respond`, unless `notify` is `never` or a `mode: wait` delegate is still waiting on the task. The message is withdrawn from the parent's queue once the question no longer waits. Such a question is the agent parent's to answer (`inputOwner: parent`), so it does not flag the person, raise the parent's needs-input state or send a push. Approvals and every other request kind, and every request in a task a person delegated, stay with the person.

Cancellation interrupts the owned child turn, cancels its queued input and recursively cancels descendants. Preparation checks cancellation before launch. Already-created workspaces remain recorded and are never deleted automatically. Restart recovery reconciles tasks with the chat store and marks interrupted work explicitly; it does not retry inference automatically.

Stopping a chat stops the work it delegated. When a person stops a chat from the app, a phone, the CLI or `chatOrchestration.interrupt`, the chat's own turn is interrupted first (with no turn running, the background work earlier turns left), and then every unsettled task the chat delegated is cancelled with its descendants. The chat's pending wakes, open and sealed, are dropped, and the stopped tasks never wake it later, so stopped children cannot restart it. A message sent to another chat with `expectReply` is left to that chat, and an agent interrupting its own descendant does not cascade.

## Agent guidance

`capabilities` lists, per provider, the models the person did not hide in their order, at most eight plus the pinned ones (configured, default, favorite and the caller's own model), with `omittedModels` counting the rest; Codex, Claude, Grok and Muse list every model. `search` (at most 200 characters) returns the first eight models whose id and label contain every word. A person without `search` keeps the full catalog. A bound caller also sees its own `providerInstanceId`, `model` and `reasoningEffort`.

A new chat an agent delegates to defaults to the agent's provider instance, its model on that instance, and its reasoning effort when instance, model and host match and `agent.options` is absent or null; `{}` clears the effort, an explicit effort wins, and a target that refuses an inherited effort is retried once without it. The task records `reasoningEffort` and `reasoningEffortSource: explicit|inherited`. A person's new chat without a provider instance fails before any workspace is prepared.

Chats and tasks carry `link`, a Markdown link `[title](alera-chat://v1/<chatId>?workspace=<workspaceId>)` that the apps open as that chat; agents mention a chat by pasting it. Each chat with the injected tools also gets orchestration instructions for its provider: Claude through its system prompt, Codex as thread developer instructions, and other providers around the first prompt after each session start or context compaction.

## Identity and permissions

Humans use the existing authenticated desktop/mobile host permissions. An injected MCP server binds to one chat generation using a random per-chat credential stored in a private file; persistence holds its hash. The hello connection verifies the credential and stamps `agent:<chatId>` and scope `chat:<chatId>`, ignoring caller-supplied identity. Credentials are revoked on provider switch and close. Bound agents need a live, unarchived caller turn, or a native sub-agent of the caller's provider process still running after its turn ended, as such a background sub-agent keeps calling tools.

Bound agents may read and message chats across known projects and hosts. They may interrupt, configure, answer requests, acknowledge results or cancel work only in their own descendant lineage. Targets cannot exceed the caller's runtime mode ceiling. `updateTitle` (MCP `chat_update_title`, `agentChatTitleGenerationV1`) renames or regenerates the title of the caller's own chat, or of a chat in its descendant lineage; an agent's title never replaces a title a person set. `requestSecret` (MCP `request_secret`, `agentChatSecretRequestsV1`) opens a masked `secret_input` card in the caller's own chat and waits up to 45 seconds, then answers `pending` with a `requestId` to wait on again. Only a person answers the card, from desktop or mobile, with `agentChat.secret.provide`; `respond` and a parent agent's `chat_respond` refuse it. The value goes straight to its delivery and never into the chat's history, snapshots, receipts or logs (it is registered for log redaction): `file` (the default and recommended mode) writes a 0600 file in a 0700 directory, and `ref` stores a one-use `secretRef` in the provider-secret store that `alera chat secret read --ref <ref>` (CLI only, `readSecret`) prints once inside another command. Both expire after 24 hours. The pull request verbs (`chatOrchestrationPullRequestsV1`; MCP `link_pull_request`, `unlink_pull_request`, `list_chat_pull_requests`, `watch_pull_request` and `unwatch_pull_request`; CLI `alera chat pr`) keep links in the additive `agentChatPullRequests` table, beside the per-workspace links and watches. A watch reads the pull request in the chat's workspace repository on the 30 second watch tick, with Watch and Fix's check classifiers, and delivers T3 Code's notices into the chat as a message with `origin.kind = pullRequestWatch`: failed checks, passed checks, new comments (those already there never wake it) and conflicts, each once per head. It stops after 10 comment-only notices in a row, after 8 failed reads in a row (both with a notice), when the pull request closes (with a notice) or merges (silently). A delegated child may link but never watch, and its link result's `next` tells it to end with `PR <url>, head <SHA>, checks and reviews <state>`. The scheduled task verbs (`chatOrchestrationSchedulesV1`; MCP `schedule_task`, `list_scheduled_tasks`, `delete_scheduled_task` and `run_scheduled_task_now`; CLI `alera chat schedule save|list|delete|run`) port T3 Code's scheduled tasks onto Alera Automations: each task is an automation with an `agentChat` target (`automationAgentChatTargetV1`). `scheduleTask` takes `{scheduledTaskId?, prompt?, title?, schedule?, enabled?, bindToCurrentChat?, chatId?, requestId?}`; a new task needs `prompt` and `schedule`, and an update changes only the fields given (`enabled: false` pauses it). `schedule` is `{type: interval, everyMs}` (at least 60000, stored as the `interval` schedule `{everySeconds, anchor}`) or `{type: fixed_time, timeOfDay: HH:MM, weekdays?, timezone?}` (stored as a recurring cron in the given IANA zone, or this computer's). There are no webhook triggers: Alera has no inbound path, so `{type: webhook}` is refused. By default (`bindToCurrentChat: true`) each run posts its prompt into the calling chat as a message with `origin.kind = automation`; with `false` each run opens a new chat in the same workspace with the calling chat's agent. A run's `runtimeModeCeiling` is the calling chat's runtime mode, an update by a lower-mode chat lowers it, and a post above it is refused at turn start (`mode_ceiling`) and blocks the run. A run ends when the chat turn that consumed its message (matched by `clientMessageId`) ends: completed is success, failed is failure, and an interrupted or cancelled turn or queued message cancels the run; there is no heartbeat and no inactivity timeout. A bound agent sees and changes only tasks in its chat's project; a delegated child may only list (`childCannotSchedule`). `deleteScheduledTask` moves the automation to the Automations trash. `runScheduledTaskNow` starts a manual run and answers `{runId, chatId, status}`; a bound caller needs a full-access chat in the default interaction mode (`runNowNotAllowed`). A person scheduling from the CLI names the chat with `--chat-id`. Host-to-host forwarding verifies the origin chat belongs to the authenticated origin host. Credentials, provider environment and MCP tokens never appear in snapshots, events, logs or task results. This identity binding does not replace an operating system sandbox.

## Runtime and storage boundaries

`AgentChatRuntime` supplies create/list/command/send/interrupt/snapshot/subscribe and `ProviderLaunchHook` runs before each native spawn. Host-only metadata records lineage; only explicit safe lineage fields are projected to clients. `SendInput.origin` records a chat message, orchestration wake or sub-agent wake so clients can distinguish it from user input. Store tasks, wakes, receipts and credential hashes separately from terminal orchestration. Receipt identity is `(scope,verb,requestId)` plus a canonical payload digest; same payload replays, a different payload conflicts. Journal/task changes commit before broadcast.

The hub owns cross-host task routing. Each satellite owns its provider processes and chat transcript. Workspace creation uses `HubSelfClientPool` and the existing `workspace.createManaged` or `workspace.createShared` flow, including setup and mutation barriers. No additional git implementation is introduced.

## Provider tool injection

The shared provider contract carries typed stdio or HTTP MCP specifications and explicit injection capabilities. The host injects `alera mcp --runtime-dir <dir> serve --chat-credential-file <private-path>` with a stable server name. Adapters validate and translate that specification to their native session configuration. Unsupported configuration returns an explicit error and is reported in the catalog; it is never silently discarded.

Codex and Claude use native MCP configuration; Cursor uses its public bridge MCP fields; ACP variants pass servers on session new/load/resume; Muse negotiates `sessionMcp`; OpenCode installs and removes per-chat servers through its HTTP API and refuses unsafe shared-server mutation; Pi uses a documented extension bridge because its RPC runtime has no native MCP boundary. Each adapter has wire fixture tests for injection. Runtime/host binaries remain external dependencies when their source or redistribution license differs from the client port.

## UI and verification

Chat Tasks is the fourth section of the existing Activity overlay/screen, alongside Runs, Questions and Automations. Chat notices link to task details, and Open Chat/Open Workspace are explicit navigation actions. Selecting a task never changes the workspace or chat. Shared Dart DTOs and repositories live in `packages/alera_agent_chat`; native frame projection remains in Rust. Older hosts show Update Required for the section, and capability gates disable delegation controls.

Verification covers durable receipt replay/conflict, workspace strategies, cross-project routing, mode ceilings, lineage mutations, live-turn credentials/revocation, concurrent wake merging, recursive cancellation, restart reconciliation, per-provider injection, MCP catalog/CLI parity and desktop/mobile repository and widget behavior. Runtime wiring and process fixtures must be tested independently from real model inference.
