# Codex chat history and delivery

## Conversation actions

Desktop and Mobile expose Fork Chat in the composer actions and Fork From Here on messages. The runtime reads the complete server history, selects a finished turn, and passes its ID explicitly to `thread/fork`. A running turn is excluded from Fork Chat. A conversation without any finished turn cannot be forked. Runtime snapshots and deltas carry `hasCompletedTurns`, so a long active turn does not hide Fork Chat when earlier finished turns are outside the visible page. The result opens a new tab in the same workspace and inherits its directory and configuration. It shares workspace files; no Git branch or worktree is created. Drafts, queued messages, and active execution are not copied. Surviving user messages retain their Alera text, attachment chips, and Steer markers, including presentation reconstructed from accepted delivery receipts.

Edit Message applies to the initial user message of a turn. The editor captures its conversation identity and history revision when opened; a conversation switch makes saving fail without modifying the new chat. Steer messages and goal messages do not offer this action. Saving explicitly confirms that later responses will be discarded and that files and actions already performed will not be undone. The runtime pauses the queue, validates the target against complete history, interrupts any active turn, waits for server confirmation, rolls back, and sends the correction. `thread/rollback` is deprecated upstream and is isolated in the history implementation. If the app-server rejects the method, editing reports that it is unavailable; it never substitutes a fork.

Synthetic messages submitted through `/goal` also disable Fork From Here because their IDs do not identify native turns. Completed native turns remain available as fork boundaries.

Retained inputs preserve attachments and structured references. Replacing history also preserves the visible text, attachments, and Steer markers of surviving user messages. Older messages with ambiguous or unavailable input report that they cannot be reconstructed safely. A failed resend after a successful rollback leaves the correction available through Retry Correction without repeating the rollback. An uncertain transport result requires reconciliation before any retry. If a native rollback succeeds but saving its recovery state fails, the conversation remains locked and paused until reconciliation confirms the retained history. Recovery restores the replacement snapshot and offers an explicit correction retry without another rollback. Reusing an edit operation ID with revised text or a different target is rejected without replacing its saved correction. Identical retries and Retry Correction without new content remain idempotent. Editing always leaves the queue paused until Resume Queue is selected.

Full native-history scans for fork, edit validation, and delivery recovery run outside the runtime actor with a bounded deadline. The runtime continues serving other clients and Stop while a scan is pending. Before applying a scan, it checks the conversation identity, queue and history revisions, and app-server instance; a changed context requires a fresh request. Reconciliations also compare the bounded live snapshot after flushing buffered deltas, so a late scan cannot overwrite a completion or request response processed during the read. Forks remain available while their source makes progress because they do not replace its history. Startup recovery uses the same deferred path and retains the runtime until it finishes.

Native fork creation and history projection also run outside the runtime actor. Stop and other clients remain responsive through both stages. The native fork receipt is persisted before projection, so a stale context or interrupted projection can be recovered with the same operation ID without creating another fork. Removing the source tab or workspace waits until this work finishes.

A definitively rejected fork can be retried with the same operation ID. An uncertain fork is not recreated automatically, and retries of a completed fork return the existing tab.

Client scans also recheck the runtime removal barrier before applying their results, so a queued tab or workspace removal cannot miss a newly created fork or correction. Internal startup reconciliation may still finish while an unrelated removal is pending; its persisted uncertain work already prevents removal of the affected conversation and reconciliation never resends it.

Desktop and Mobile allow seven minutes for fork, edit, and queue reconciliation responses, covering initialization, the bounded history scan, and subsequent native requests. Other requests retain their normal transport deadlines. A delayed success or rejection preserves the original operation identity; a timeout never triggers an automatic resend.

History editing refuses to truncate a conversation while a delivery remains uncertain, preserving the server evidence needed for reconciliation. Fork selection inserts the persisted tab into the workbench layout before focusing it, without waiting for the debounced tab notification.

Paginated native conversations do not support rollback. The runtime checks this mode before interruption or history changes when the server exposes it, and remembers explicit unsupported-method responses for the conversation. Edit Message is then disabled with an explanation. This restriction was verified against Codex 0.151.0 and is documented in the [OpenAI app-server protocol](https://github.com/openai/codex/blob/main/codex-rs/app-server/README.md). There is no supported conversion to legacy history mode. Fork and queue operations remain available; history validation can hydrate paginated items through `thread/items/list`.

## Runtime queue

The `codexChatState` table stores delivery state separately from editable workspace tab payloads. Entries retain their stable client message ID, ordering, revision, structured input, presentation, captured configuration, and delivery state. The runtime alone dispatches shared queues. Normal messages are FIFO, triggered by acceptance/completion events and startup reconciliation, without a recurring polling loop. Executable pending work prevents idle shutdown even with no connected application. Completion events retain the runtime while a history operation or delivery is still executing, even when its queue is paused.

Startup normalizes persisted delivery state locally and defers Codex initialization, conversation resume, and history projection to background jobs. Recovery and incoming clients share one initialization attempt. Other runtime clients remain responsive while native recovery waits. Results are checked against the captured conversation, queue/history revisions, snapshot, and server instance before installation. Failed initialization pauses pending delivery and retains its input. If a queued runtime removal is canceled when its requesting client disconnects, clearing the final removal barrier wakes blocked queues even without connected applications.

This deferred path includes edits already in `rolledBack` or `resendFailed`: the saved rollback result is projected in the background and installed only after validation. The correction remains available for explicit retry, with the queue paused and no automatic resend.

Desktop submissions made during initial opening wait for capability discovery before being accepted. Their captured text, attachments, and references remain available to the existing draft-restoration path if opening or insertion fails.

The queue shows three compact rows above the composer and expands into a vertically scrolling list. Each row exposes Steer, Remove Queued Message, and Edit Message. Editing uses a separate editor and preserves queue position and the composer's draft. A stale revision leaves the edit visible instead of overwriting another client's changes. Removing, steering, or editing a rendered row carries its stable ID and revision, so a concurrent queue change cannot redirect removal to another message. Stop also pauses the queue. For shared queues, stopping an active turn uses one runtime operation that validates the captured conversation, pauses the current queue, and interrupts the captured turn without relying on a client queue revision. Closing a tab with pending messages asks to cancel them for all connected clients. Bulk close gathers every queue and unsaved-editor confirmation before cancelling any messages.

The runtime copies uploaded attachment files into private durable storage before acknowledging a queue insertion. Workspace mentions continue to refer to workspace files. Missing or concurrently changing attachments reject insertion. Queue copies do not depend on prompt-upload expiration. Canceling removes private copies exclusively owned by pending entries. Accepted files remain available to native history and forks after closing a tab; automatic reclamation of accepted history files is intentionally not performed. Limits are 100 pending entries, 32 MiB per attachment, and 128 MiB of attachments per insertion.

Delivery states are `queued`, `sending`, `accepted`, `failed`, `uncertain`, and `removed`. Accepted and removed entries are excluded from presentation snapshots. A rejection retains the entry, records the error, and pauses the queue. An uncertain result is checked against persisted server user-message identities; it is never automatically resent. Accepted receipts restore their visible text, attachments, and Steer markers directly into the final history snapshot, including after a crash before presentation was saved. Delivery and accepted-edit reconciliation preserve pending approvals and questions belonging to the same surviving active turn, including older requests without an explicit turn ID. Requests from other or completed turns are removed; an actual rollback still clears requests. Reconciliation of the same conversation preserves its current goal, including updates or clearing processed while native history is being read. An unsuccessful Steer remains queued and is never converted into a new turn. Steer captures its target thread and turn and uses the active turn's configuration.

## Protocol and compatibility

The additive capabilities `codexForkV1`, `codexHistoryEditV1`, and `codexSharedQueueV1` are independently advertised by runtime status/control files and `mobile.hello`. No strict protocol version changes. Older runtimes retain local queue behavior and show unavailable history actions.

| Endpoint | Purpose |
| --- | --- |
| `codex.thread.fork` | Fork a captured thread through `lastTurnId`, using `operationId` |
| `codex.thread.edit` | Start or recover an edit using `operationId`, target IDs, and `expectedHistoryRevision` |
| `codex.queue.get` | Fetch the current queue snapshot |
| `codex.queue.add` | Persist input with `clientUserMessageId`; optional `turnId` requests Steer only |
| `codex.queue.edit` | Replace content by `messageId` without changing order or captured policy |
| `codex.queue.remove` | Remove one pending entry by ID |
| `codex.queue.pause` / `codex.queue.resume` | Change queue dispatch state |
| `codex.queue.steer` | Deliver one queued entry to the captured active turn |
| `codex.queue.reconcile` | Check uncertain deliveries against server history |
| `codex.queue.cancel` | Cancel pending messages after explicit close confirmation |

Mutations include `tabId` and the captured `expectedThreadId`. Queue mutations other than insertion require `expectedRevision`; a conflict returns the authoritative snapshot. Queue snapshots are published through `codexQueueChanged`. History replacement increments `historyRevision` and publishes `codexThreadChanged` with `replaceHistory: true`. Clients discard older snapshots and invalidate pending history pages. The runtime also rejects late notifications from discarded turns using the same modern, legacy, and item-level identities as the timeline reducer. All supported terminal notifications, including legacy task completion, failure, abort, and interruption, wake queue processing and refresh runtime activity. An explicit old turn ID cannot clear a newer active turn, and late delivery acknowledgements cannot reactivate a turn already marked complete. A completion without a turn ID records the active turn immediately before applying the event, including when start and completion arrive in one batch.

Switching conversations pauses the old conversation's queue without moving messages to the new conversation. Resuming that conversation restores its queue. Closing a tab confirms cancellation of pending entries from all conversations previously bound to that tab, validating their revisions together. Workspace removal refuses pending delivery or incomplete history edits until they are resolved.

Clients fetch authoritative queue state after reconnecting or observing another client's conversation switch. Desktop refreshes chat capabilities from a successful runtime status response before selecting the delivery path; a transient status failure blocks delivery rather than pretending the runtime was downgraded. An upgrade transfers pending local entries with their stable identities and preserves a paused queue. Failed or unacknowledged transfers retain pending input for Retry. A downgrade with shared pending entries keeps those rows unavailable for local dispatch until a compatible runtime reconnects; an empty shared queue can return to legacy behavior. Reopening another conversation resets the previous queue revision. Closing after missing-rollout recovery normalizes the unbound current thread to null while retaining the explicit IDs and revisions of older queues. A newer history revision in a queue snapshot triggers an authoritative history reload in both clients even when goals are unavailable. Submissions wait for that reload, and a failed reload keeps stale history blocked until Retry succeeds. Pending submission IDs survive controller disposal in the local draft store, scoped to the host, tab, and conversation, and are cleared on explicit tab closure. Failed session transitions preserve shared snapshots without merging local copies. With older runtimes, local submissions accepted while New Chat or Resume is pending survive an early conversation-change event and are sent once the transition completes. External conversation switches still clear the previous local queue. A Steer persisted before a runtime interruption keeps its captured turn target during recovery; an expired target leaves the entry failed and the queue paused.

If the Codex process exits, pending queues pause and in-flight deliveries and history operations preserve their uncertain status for reconciliation. Output read failures, including invalid UTF-8, also require reconciliation instead of retrying an unconfirmed operation. A later transport failure cannot overwrite the recorded rollback phase or unlock history before reconciliation. Resume Queue loads the conversation into the replacement app-server before dispatch, independently of the disposable client snapshot cache. It checks the restored active turn and missing-rollout state before sending. Completed deliveries no longer retain an idle runtime after its active turn is cleared, including when startup reconciliation replaces a stale active snapshot with completed native history.

Missing-rollout recovery preserves the response capabilities and queue metadata in both clients. Clearing the missing thread also clears its history revision and turn markers, so the replacement conversation starts with its own revision.

Drafts remain local until accepted by the runtime. Independent submissions receive distinct identities even when their content is identical; failed attempts retain separate IDs for retry. A rejected submission restores visible composer text, attachments, references, and selection while preserving any newer draft typed during the request. Sharing is limited to clients of the same runtime. Manual queue reordering and synchronization between different runtimes are outside this feature.

## Validation

Validated with the repository's Flutter 3.44.8 toolchain and clean analysis in both packages. Desktop passed all 3,459 tests with one skipped. Mobile passed all 672 tests with three skipped. Rust formatting and workspace Clippy passed. Rust workspace tests passed with the documented intermittent `cancelling_active_worker_interrupts_before_idle_banner_delivery` PTY case run separately (2,011 passed in total, 4 ignored). Earlier full runs exposed unrelated AgentAwakeService and transcript-watchdog timing assertions; both passed in isolation and in the final Desktop suite. A tab-removal/emulator ordering test failed once under full-suite load, then passed in isolation and in the final Rust workspace run.

An isolated development runtime with Codex 0.151.0 exercised real delivery, fork, concurrent queue changes, stale revision rejection, attachment retention, and paused queue persistence across restart. Native editing correctly reported the paginated-history restriction without changing the original conversation. Widget renders cover compact and narrow layouts, attachments, long text, and editor conflicts. Android chat verification uses a temporary test entry point because the normal development APK stalls before its first frame during service bootstrap; this does not establish that the normal Android bootstrap is healthy.
